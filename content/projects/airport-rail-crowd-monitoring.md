_2025.11 ~ 2026.01_

## 개요

계양역 관제 담당자는 역사 내 CCTV 영상을 확인한 뒤 시간대별 혼잡도와 현장 상황을 수기로 정리해
보고하고 있었다. 여러 CCTV를 직접 확인하고 통계 자료를 작성해야 해 업무 부담이 컸으며, 혼잡도가
높은 구역을 즉시 파악하기도 어려웠다.

이를 개선하기 위해 **RTSP CCTV 영상을 실시간으로 수집하고, AI 객체 탐지 결과를 기반으로 혼잡도를
계산해 영상·통계·보고서 형태로 제공하는 내부 관제 웹 시스템**을 구축했다.

시스템은 인터넷 접속이 불가능하고 허용 포트가 제한된 계양역 폐쇄망에서 동작해야 했다. 총 48개
CCTV의 실시간 영상과 바운딩박스를 제공하고, 그중 주요 12개 채널에 대해 혼잡도 분석 및 통계
기능을 적용했다. 혼잡도는 공간 면적 대비 인원 수를 기준으로 산출했으며, 혼잡도가 높은 CCTV를
우선 노출해 관제 담당자가 주요 구역을 빠르게 확인할 수 있도록 구성했다.

PoC 형태로 진행됐지만 실제 계양역 관제 담당자가 업무에 사용했으며, 기존 수작업 보고 과정의
일부를 자동화했다.

## 역할

9명 규모의 프로젝트에서 백엔드·인프라 담당으로 참여했다.

**직접 수행한 업무**

- 전체 시스템 아키텍처 초안 설계 및 팀 협의를 통한 구조 확정
- FastAPI 기반 백엔드 API 설계 및 개발
- OpenCV `VideoCapture` 기반 RTSP CCTV 연결 및 프레임 수집, 카메라별 수집 스레드와 제한된 작업 풀 구성
- 연결 실패 시 재접속 및 상태 확인 로직 구현
- YOLO 모델 파일 로딩 및 추론 결과 연동, 좌표를 프론트엔드용 바운딩박스 JSON으로 변환
- WebRTC 기반 실시간 영상 전달 구조 연동
- PostgreSQL 스키마 및 통계 테이블 설계, 프레임 단위 결과 적재와 5분 단위 통계 집계
- 카메라·날짜·시간 조건의 통계 조회 API 개발
- Nginx upstream 라우팅, CORS 및 프록시 설정
- FastAPI lifespan 기반 모델 로딩, warm-up 및 초기화 처리
- Docker health check, 오류 재시도 및 운영 로그 확인
- 폐쇄망 현장 배포, 장애 대응 및 사용자 가이드 작성
- 프론트엔드·모델 개발자와 API 규격 및 데이터 형식 조율

**협업한 업무**

- 모델 개발자가 학습한 YOLO·COCO 기반 객체 탐지 모델 적용 (일반 CCTV용 사람 탐지 + 에스컬레이터용 캐리어 탐지)
- GPU별 백엔드 컨테이너 분리 및 카메라 번호 기준 upstream 라우팅
- Dockerfile, Docker Compose 초기 구성 및 CUDA 환경 설정
- 프론트엔드 화면 및 통계 대시보드 개발

## 구조도

![공항철도 실시간 혼잡도 분석 시스템 아키텍처](/static/images/projects/airport-rail-crowd-monitoring/architecture.svg)

12개 채널의 CCTV가 RTSP로 폐쇄망 단일 서버에 연결된다. 서버 사양은 다음과 같다.

- **CPU** W5-3553X × 1, **Mem** DDR5 4800 32GB × 4
- **Disk** 990 Pro NVMe 1TB(시스템/모델) + Seagate SkyHawk AI 10TB(영상/데이터)
- **GPU** RTX 5090 32GB × 2
- **OS/런타임** Ubuntu 24.04, CUDA 12.4, PyTorch 2.5.1 + cu124, Docker

Docker로 띄운 컨테이너들은 이렇게 연결된다.

1. RTSP로 들어온 1~6채널 영상은 GPU 0, 7~12채널 영상은 GPU 1이 나눠 맡아 `Master` 컨테이너의
   `Model`(캐리어·혼잡도 탐지)에서 추론하고, 결과 이미지를 같은 컨테이너의 `FastAPI`로 전달한다.
2. `FastAPI`는 RTSP 원본 영상과 `Model`의 추론 결과 이미지를 함께 받아 `WebRTC` 컨테이너로
   넘기고, 상태·설정 정보는 `Postgre`(PostgreSQL)에 별도로 기록한다.
3. `WebRTC`는 12채널 영상을 `FrontEnd`로 스트리밍하고, `FrontEnd`는 `Option API`로 `FastAPI`와
   설정값을 주고받는다.
4. `FrontEnd`가 만든 웹페이지는 `Nginx`를 거쳐 관제 담당자의 브라우저로 전달된다.

## 문제 및 해결

### 1. 다채널 RTSP 영상의 지연 누적

**문제** — OpenCV `VideoCapture` 기본 설정으로 RTSP 스트림을 수신하면 버퍼에 쌓인 이전 프레임이
순차 처리되면서, 실제 현장보다 늦은 화면이 전달됐다. 12개 분석 채널을 동시에 처리해야 해서
지연이 누적되면 실시간 관제로서 활용도가 크게 떨어졌다.

**해결** — `VideoCapture` 버퍼 옵션을 조정해 오래된 프레임 누적을 최소화하고, 카메라별 독립
수집 스레드를 구성해 대기 중인 과거 프레임 대신 최신 프레임을 유지하도록 변경했다. 동시
요청·결과 전달 구간에는 비동기 처리를 적용하고, RTSP 연결 실패 시 일정 시간 내 최대 5회
재연결을 시도했다. Health check API와 Docker Compose health check + restart policy로 장애
시 복구 가능하도록 구성했다.

**결과** — 12개 채널이 연결된 환경에서 RTSP 프레임 수신부터 WebRTC 전달 전 처리 구간의 평균
지연을 **0.5초에서 0.1초로 약 80% 단축**했다.

### 2. 장기간 원본 데이터 조회로 인한 통계 API 지연

**문제** — 카메라마다 초당 6프레임을 처리해 사람 수·혼잡도 점수·시간 정보를 PostgreSQL에
저장했다. 1년치 12개 카메라 데이터를 통계 화면에서 조회하면 원본 프레임을 매번 집계해야 해
응답에 약 10초가 걸렸고, 데이터가 쌓일수록 더 느려지는 구조였다.

**해결** — 프레임 단위 원본 데이터와 5분 단위 통계 데이터를 별도 테이블로 분리하고, 정각
기준 고정된 5분 구간별로 카메라별 혼잡도 점수의 평균·최대·최소를 저장했다. 통계 적재는 별도
스레드에서 처리해 실시간 API 요청과 분리하고 실패 시 재시도하도록 했다. 카메라 번호·시간
범위 조회 조건에 맞춰 인덱스를 구성하고, 1년이 지난 데이터는 삭제하는 정책을 적용했다.

**결과** — 1년 기간, 12개 카메라 기준 통계 조회 시간을 **약 10초에서 5초로 50% 단축**했다.

### 3. 인터넷 접속이 불가능한 폐쇄망 배포

**문제** — 계양역 서버는 인터넷에 연결할 수 없고 사용 가능한 포트도 제한돼 있었다. 현장에서
Docker 이미지를 내려받거나 외부 API와 연결할 수 없었고, Backend·Frontend·DB·WebRTC 서버를
하나의 물리 서버에서 안정적으로 운영해야 했다.

**해결** — Backend, Frontend, PostgreSQL, Nginx, Coturn을 컨테이너 단위로 구성하고 Docker
이미지를 tar 파일로 패키징해 USB로 현장에 반입, 서버실에서 직접 로드해 배포했다. 외부 접근
지점을 Nginx로 통합해 허용된 포트 안에서만 내부 컨테이너로 라우팅하고, FastAPI 포트는 직접
노출하지 않았다. PostgreSQL 데이터와 모델 파일은 호스트 볼륨에 영속화했고, 모델 파일을 이미지에
포함하지 않고 볼륨 마운트해 교체 편의성과 이미지 용량을 개선했다. 운영자가 쉽게 서비스를
확인·재기동할 수 있도록 명령어 alias와 사용자 가이드를 제공했다.

**결과** — 외부 네트워크 의존 없이 폐쇄망 단일 서버에서 전체 시스템을 배포했고, 계양역 관제
담당자가 실제 혼잡도 확인과 보고 업무에 활용할 수 있는 환경을 구축했다.

### 4. GPU 및 모델별 요청 분산

**문제** — 서버의 GPU 2장을 효율적으로 써야 했고, 일반 CCTV와 에스컬레이터 CCTV는 서로 다른
목적의 모델을 사용해야 했다. 하나의 Backend에 모든 요청을 집중시키면 특정 GPU에 부하가
몰리고, 카메라 종류에 따라 적절한 모델 경로를 선택해야 했다.

**해결** — FastAPI Backend 컨테이너를 2개로 분리해 각각 GPU 번호를 지정하고, 카메라 번호의
짝수·홀수 기준으로 Nginx upstream을 나눠 요청을 분산했다. 일반 CCTV는 사람 탐지 모델, 에스컬레이터
CCTV는 캐리어 탐지 모델 경로로 전달했다. 애플리케이션 시작 시 모델을 한 번 로딩하고 warm-up을
수행해 초기 추론 지연을 줄였고, 모델 파일을 볼륨 마운트해 변경 시 이미지를 다시 만들지 않도록 했다.

**결과** — 48개 CCTV 영상 스트리밍과 바운딩박스를 제공하면서, 주요 12개 채널의 혼잡도 분석
요청을 두 GPU에 분산해 처리했다.

### 5. 영상 개인정보 보호

**문제** — 역사 CCTV 영상에는 실제 이용객의 얼굴이 포함돼, 관제 웹페이지에 원본 영상을 그대로
노출하면 개인정보 문제가 생길 수 있었다.

**해결** — AI 탐지 결과를 활용해 영상 내 개인정보 대상 영역에 블러 처리를 적용하고, 처리된
영상을 WebRTC 방식으로 전달했다.

**결과** — 실시간 관제 기능을 유지하면서 CCTV 영상 사용에 따른 개인정보 노출 위험을 줄였다.

## 성과

- 계양역 관제 담당자가 실제 사용한 실시간 혼잡도 분석 및 보고 자동화 시스템 구축
- 총 48개 RTSP CCTV 채널의 실시간 영상 및 바운딩박스 제공, 주요 12개 채널에 AI 기반 혼잡도 분석·통계 적용
- 일반 CCTV 사람 탐지 / 에스컬레이터 캐리어 탐지 모델 분기, 2개 Backend·GPU별 Nginx upstream 라우팅
- WebRTC + Coturn 기반 폐쇄망 실시간 영상 전달
- RTSP 처리 지연 0.5초 → 0.1초 (약 80% 개선), 1년 통계 조회 10초 → 5초로 단축
- 날짜·시간·카메라별 혼잡도 조회, 1시간 단위 그래프, 혼잡 알림, 보고서 다운로드 기능 제공
- 인터넷이 차단된 현장 서버에 Docker 이미지와 모델을 직접 반입해 배포

## 회고

AI 모델의 정확도만으로는 실제 서비스를 완성할 수 없으며, 영상 수집·모델 추론·데이터 적재·통계
조회·실시간 전송·폐쇄망 배포까지 전체 파이프라인이 안정적으로 연결돼야 한다는 점을 경험했다.

특히 RTSP 영상은 일반적인 API 데이터와 달리 연결 불안정, 버퍼 누적, 프레임 지연, 장시간 실행에
따른 메모리 증가 등 운영 관점의 문제가 지속적으로 발생했다. 이를 해결하는 과정에서 카메라별
스레드 관리, 최신 프레임 유지, health check, 재접속 및 정기 재기동 등 실시간 영상 서비스 운영에
필요한 구조를 적용했다.

다만 PoC 일정 내에서는 일부 영역을 운영 안정화 방식으로 대응했다. 장시간 구동 시 발생하는 메모리
증가 문제는 health check와 비사용 시간대 정기 재기동으로 완화했으나, 근본적인 원인을 완전히
분석하지는 못했다. 향후 고도화한다면 다음을 개선하고 싶다.

- 카메라 스레드별 메모리 사용량과 OpenCV 객체 수명 모니터링
- 카메라 스레드에서 직접 DB를 호출하지 않고 메시지 큐와 전용 DB writer 적용
- 프레임 단위 개별 INSERT를 일정 단위의 bulk insert로 변경, 스레드별 SQLAlchemy Session 경계 명확화
- `(camera_id, interval_start)` 복합 유니크 키와 upsert로 통계 중복 방지
- 날짜 기준 파티셔닝 및 월·일·시간 단위 사전 집계 테이블 추가
- Prometheus·Grafana 기반 FPS, 지연시간, GPU, VRAM, 메모리 모니터링
- 혼잡도·트래픽 패턴을 Prophet·LSTM 등 시계열 예측에 활용해 이상 혼잡 상황을 사전 탐지하고
  GPU 리소스를 미리 조정하는 AIOps 검토
- 장애·이상 탐지 로그를 자동 분석해 초기 보고서를 생성하고, 재기동 등 반복 운영 작업을
  AIOps로 자동화
- 서버 재부팅 이후 전체 컨테이너 자동 기동 구성
- 모델별 정확도와 실제 관제 결과 간 정량 검증 체계 추가
